# The recorder drops looping CDN data instead of recording it

CDN edge nodes occasionally fail by replaying the same byte window over and over. The health watchdog cannot see this — bytes keep growing — so the pump would record the repeated content indefinitely. The record pump now groups tags into blocks (video keyframe to video keyframe, with fallback boundaries at a 25s timestamp gap, a 60s block span, and 64MB of buffered data, which is the only boundary audio-only streams get), buffers each block, and on block close compares an order-dependent content fingerprint (FNV-1a over tag types and payloads, timestamps excluded since replays may rewrite them) against the last 16 blocks. A duplicate block is dropped without being written; after 10 consecutive duplicates the pump aborts with an `ErrStreamTransient`-wrapped error, which sends the stream-drop decision tree through a fresh `OpenLiveStream` — effectively changing CDN nodes. Duplicate drops reset the health-check failure rounds because the stream is demonstrably alive. Making the write path one block lazy had two consequences kept deliberately: split decisions evaluate after the pending block lands (so time/size checks see current segment state), and the forced-split and stream-end paths flush the pending block first, so no accepted data is left buffered when a segment closes.
