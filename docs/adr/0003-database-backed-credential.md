# The Bilibili credential lives in the database, obtained via web QR login

The Bilibili cookie used to be a deployment-time constant copied by hand from a browser into `configs/credentials.yaml`, with no rotation story — when it expired the recorder silently lost source quality until someone re-copied it. The credential is now a singleton row in the sqlite `credentials` table, obtained through web QR login (`/v1/account/qr-login/*` calling Bilibili's passport endpoints) and the only cookie source; `recorder.cookie` stays in `conf.proto` but is deprecated and ignored. Activation is a data-layer side effect of `CredentialRepo.Save`/`Delete`: each persists first, then hot-swaps the in-memory cookie held by `*Data` (now guarded by a mutex and read through one accessor, with the WBI signer taking a cookie provider instead of a startup snapshot), so a fresh login takes effect without restarting the recorder. Logout is local-only — it deletes the row and clears memory, and never calls Bilibili's logout endpoint. In-flight connections (a live danmaku websocket or an open stream body) keep the cookie they started with until their next redial, which is acceptable.
